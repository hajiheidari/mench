# Coins and cosmetics (M12)

Coins are non-monetary points, not wagers or withdrawable currency. Only a server-recorded completed online match grants rewards:100 to each registered winner,40 to registered participants, at most five rewards per UTC day. Offline/bot play grants none. Coins buy two original visual themes (Aurora60, Sunset80); theme changes never enter engine/dice/rating code. No payment/real-money/store integration.

Final game snapshot, unique result, rating changes and match rewards commit together. User rows and wallet rows lock in canonical order. Reward references use match+wallet UUIDs and prevent double credit. Purchase API accepts SKU and UUID request ID only; price comes from server catalog. Wallet lock serializes concurrent spends, and database enforces nonnegative balances. Matching retries return success without charging again; different SKU with same ID fails. Inventory is unique per wallet/SKU; equipment requires ownership. Browser/native share typed API and account views; selection is persistent across device sign-ins.

Immutable ledger records positive rewards and negative purchases, each with unique reference and nonsecret metadata. Database triggers reject UPDATE/DELETE. Wallet balance and receipts are checked in tests; GET uses a repeatable-read snapshot and returns latest50 entries. Balance/deltas are decimal strings to avoid JavaScript integer precision loss. Account deletion anonymizes wallet ownership while retaining append-only financial audit; no email/name/session enters receipts. Audit retention, anonymization policy and separate production DB roles still require release review. Tests retain anonymous append-only fixtures rather than disabling guards.

Actual PostgreSQL cases cover concurrent repeated settlement, immutable receipts, simultaneous overspend attempts, price forgery, matching/mismatched request retries, duplicate ownership, equipment checks, sum-of-ledger reconciliation and five-game budget. Browser purchase fixture credits a new test-only wallet with a balanced receipt; production has no public grant endpoint. Native UI exports do not prove device execution.

Production abuse controls (collusion/farming/multiple accounts), daily reward tuning and scheduled reconciliation/operational alerts remain hardening work. Refund/admin adjustments are not implemented; future adjustments must append compensating receipts, never rewrite history.
