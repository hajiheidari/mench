# MASTER PROJECT PROMPT
## Build a Production-Grade Cross-Platform Online Ludo Game

You are the principal software architect, senior full-stack engineer, multiplayer game engineer, DevOps engineer, QA engineer, and security reviewer for this project.

Your responsibility is to build a completely original, production-quality online Ludo/Manch game from an empty GitHub repository.

This is NOT a clone of Mencherz or any other existing application.

Do not copy proprietary source code, artwork, UI, sounds, names, branding, layouts, animations, text, or assets from Mencherz or any competitor.

The product must have its own architecture, visual identity, UX, game presentation, and brand.

Existing Ludo applications may only be treated as market references.

---

# 1. PRODUCT VISION

Build a standalone online Ludo game available as:

1. Responsive Web Application
2. Installable PWA
3. Android application
4. iPhone/iOS application

All platforms must connect to the same backend, account system, multiplayer infrastructure, economy, ranking, friends system, statistics, and game state.

A user should eventually be able to:

- create an account on the website,
- play from a browser,
- install the Android/iOS application,
- log into the same account,
- and retain all progress, friends, cosmetics, statistics, rankings, coins and history.

The architecture must NOT depend on a larger multi-game platform.

This is a standalone product.

However, code should still be modular and reusable where reasonable.

# 5. CORE ARCHITECTURAL RULE

THE SERVER IS AUTHORITATIVE.

Clients must never decide:

- dice outcomes
- legal moves
- captures
- turns
- game results
- rewards
- ranking changes
- coin transactions

Clients send intents.

Server validates them.

Example:

Client:

MOVE_PAWN pawnId=3

Server:

validate turn
validate ownership
validate legal movement
apply movement
check capture
check home
check victory
persist state
broadcast authoritative result

This principle must be maintained throughout the project.

# 8. FAIR DICE SYSTEM

This is a major product differentiator.

Users must never need to trust the server blindly.

Design a cryptographically verifiable dice mechanism.

Investigate an appropriate commit/reveal design.

Potential approach:

Before the roll:

server generates secret seed

server publishes:

SHA256(secret + contextual data)

After the roll:

server reveals the required verification information.

The user should eventually be able to inspect:

Game History
→ Dice History
→ Verify Roll

and independently verify that a roll was not modified after commitment.

IMPORTANT:

The dice algorithm MUST NEVER use:

- player spending
- purchases
- coin balance
- losing streak
- winning streak
- table value
- account age
- VIP status
- advertisements
- engagement metrics

to manipulate outcomes.

Document the complete algorithm.

Create automated statistical tests.

Run large simulations.

At minimum test:

100,000 rolls during development.

Before production readiness:

1,000,000+ simulated rolls.

Check approximate distribution.

Also test reproducibility and commitment verification.
