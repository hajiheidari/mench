# ادامهٔ پروژهٔ منچ و تحویل روی سایت موجود من

من صاحب این پروژه‌ام. سورس کامل بازی منچ را از Codex تحویل گرفته‌ام و می‌خواهم تو، Claude Code، توسعه را ادامه بدهی و بازی را روی سایت موجود من بالا بیاوری. طرح چند بازی دیگر و زمینهٔ سایت در محیط کاری تو موجود است؛ ابتدا همان پروژه، دستورالعمل‌هایش، زبان طراحی، زیرساخت و مسیر انتشار را بررسی کن. آن اطلاعات در محیط Codex موجود نبود، پس در این تحویل هیچ دامنه، حساب هاست یا معماری سایتی فرض نشده است.

**این پروژه از صفر نیست. کد کارکرده را ادامه بده؛ از M0 دوباره شروع نکن.** این دستور جدید و تصمیم‌های بعدی من بر قسمت‌های تاریخی پرامپت اولیه، مانند «بعد از هر milestone توقف کن»، مقدم‌اند. من قبلاً خواسته‌ام تا جایی که واقعاً به اطلاعات یا دسترسی من نیاز نیست، پیوسته ادامه بدهی. کپی‌برداری از کد یا دارایی اختصاصی بازی‌های دیگر مجاز نیست.

## ورودی‌ها و ترتیب مطالعه

1. `AGENTS.md` در ریشهٔ سورس، همچنین دستورالعمل‌های سایت مقصد.
2. همین پرامپت؛ شرح به‌روز درخواست‌ها و مسیر ادامه است.
3. `docs/handoff/ORIGINAL_MASTER_PROMPT.txt`؛ متن کامل و دست‌نخوردهٔ پرامپت اولیه. نسخهٔ کامل آن در انتهای پرامپت دانلودی تحویل نیز ضمیمه می‌شود.
4. `docs/PROJECT_STATUS.md`, `docs/ARCHITECTURE.md`, `docs/DECISIONS.md`, `docs/adr/`, `docs/KNOWN_ISSUES.md`, `docs/TESTING.md`.
5. `docs/DICE_AND_ONLINE_REVIEW.md`, `docs/VISUAL_DESIGN.md`, `docs/CLASSIC_COLORS_VALIDATION_REPORT.json`, `docs/VISUAL_VALIDATION_REPORT.json`.
6. برای انتشار: `docs/HARDENING.md`, `docs/SECURITY_REVIEW.md`, `docs/STORE_READINESS.md`, `docs/MOBILE.md`, فایل‌های production و دستورالعمل‌های عملیات داخل docs و infra.

اسناد بعضی milestoneها تاریخی‌اند. تاریخ و محدودهٔ هر گزارش را بخوان؛ تست یا هش قدیمی را به نسخهٔ جدید نسبت نده. به عنوان مثال ابتدای PROJECT_STATUS از ۹ تست E2E قدیمی صحبت می‌کند؛ بعد از اصلاحات UI، ۱۲ تست وب پاس شده‌اند. «پیاده‌سازی شده» مساوی «منتشر شده» یا «روی گوشی واقعی تست شده» نیست.

## محصول و وضعیت فعلی سورس

هدف اولیه: منچ مستقل و اصیل با وب واکنش‌گرا، PWA، Android و iOS، یک بک‌اند و قواعد/حساب/دوستان/رتبه/اقتصاد مشترک. خواستهٔ جدید من این است که روی سایت موجودم عرضه شود. پوسته و ورود از سایت را یکپارچه کن، ولی موتور و پروتکل مشترک را مستقل و قابل استفاده مجدد نگه دار. بدون بررسی، بک‌اند و سیستم حساب سایت را حذف یا با یک سیستم تازه جایگزین نکن. اگر سایت حساب مشترک دارد، قرارداد اتصال و مجوزدهی را روشن و امن پیاده کن؛ توکن نامرتبط را مستقیم به API بازی نده.

مخزن اصلی `hajiheidari/mench` است. تغییرات در شاخهٔ محلی `work` commit شده‌اند؛ انتشار، push و اجرای CI روی GitHub انجام نشده‌اند. فایل ZIP تحویل شامل snapshot کامل فایل‌های تحت کنترل نسخه است؛ فایل Git bundle جداگانه امکان بازیابی تاریخچهٔ commitها را فراهم می‌کند. از همان snapshot تحویل شروع کن، نه از main قدیمی روی GitHub.

پشتهٔ واقعی انتخاب‌شده، نه صرفاً پیشنهاد پرامپت اولیه:

- npm workspaces، TypeScript strict، Node 24.19.0، npm 11.9.0.
- `apps/web`: React 19 + Vite، PWA و رابط فارسی/انگلیسی.
- `apps/mobile`: React Native 0.86.3 + Expo SDK 57، Android/iOS/web.
- `apps/api`: Fastify + Socket.IO و PostgreSQL با migrationهای SQL. جایگزینی خودکار با Next/Nest/Prisma لازم نیست.
- Redis در محیط توسعه اختیاری است؛ مالکیت اتاق فعلاً تک‌پردازه است، نه توزیع‌شده.
- packages مشترک: موتور deterministic، game-protocol، game-client، fair-dice، game-bot، localization، board-geometry، shared-types و validation.
- Vitest، Playwright، Docker/Compose و workflowهای GitHub Actions.

پیاده‌سازی موجود شامل بازی ۲/۳/۴ نفره با چهار مهره برای هر نفر، خانه امن/زدن/مسیر خانه/پایان دقیق، اتاق آنلاین و لینک دعوت، reconnect و recovery دیتابیس، حساب ایمیلی و مهمان، session قابل ابطال، دوستان/بلاک/گزارش، صف بازی سریع و رتبه‌ای، Elo دونفره، ledger سکهٔ غیرپولی و cosmetics، ربات آفلاین سه‌سطحی، تورنمنت پایهٔ ۴/۸/۱۶/۳۲ و moderation با audit، تاریخچه و replay قابل بررسی است. کیفیت/پوشش هر بخش را در کد و گزارش‌ها بررسی کن؛ ادعای تکمیل همهٔ بندهای پرامپت اولیه نداریم.

## درخواست‌های واقعی من و اصلاحات انجام‌شده

### ظاهر، فارسی و رنگ‌ها

من کیفیت گرافیک را با این بازی بازار مقایسه کردم:
https://cafebazaar.ir/app/com.incytel.mencherz

این فقط مرجع سطح کیفیت است، نه مجوز کپی کد، دارایی یا هویت بازی. Codex نتوانست تصاویر آن را ببیند: بازار و Google Play با HTTP403 پاسخ دادند. هیچ تطبیق دقیق یا دیدن آن تصاویر ادعا نشود. در محیط تو از طرح‌های قبلی سایت و تصاویر مرجع قابل دسترسی استفاده کن و هویت اصلی بازی را نگه دار.

رابط اولیه خیلی ساده بود. اکنون برد و مهره‌های برجسته، آواتارهای کارتونی، قاب تزئینی، خانه‌های فرورفته، تاس نقطه‌دار، پس‌زمینهٔ بنفش و کنترل‌های جدید ساخته شده‌اند. طراحی هنوز باید با زبان بصری سایت من هماهنگ و روی دستگاه واقعی بازبینی شود.

**رنگ‌های بازیکنان نوستالژیک‌اند: قرمز، سبز، زرد و آبی.** اسم مرجانی و طلایی برای بازیکنان استفاده نشود. English هم Red/Green/Yellow/Blue است. آواتار هر نفر باید رنگ خود مهره/خانه را داشته باشد؛ صورت هلویی برای قرمز و یال نارنجی برای زرد اصلاح شده‌اند. تغییر پالت، نام‌ها یا ارتباط رنگ‌ها بدون خواستهٔ من انجام نده. قاب تزئینی طلایی یک رنگ بازیکن نیست.

فونت فارسی سیستم خشک و رسمی بود؛ Samim/صمیم regular و bold به صورت محلی با مجوز upstream بسته‌بندی شده است. در وب، APK و HTML آفلاین از همین فونت استفاده می‌شود، نه فونت CDN یا فونت نصب‌شده روی گوشی. RTL، خوانایی، اندازهٔ لمس، contrast و responsive حفظ شوند.

هنر مشترک در `packages/board-geometry/src/art.ts` است؛ وب SVG را مستقیم استفاده می‌کند، PNGهای native با `node scripts/build-game-art.mjs` تولید می‌شوند. بعد از تغییر هنر حتماً PNGها را بازتولید کن.

### پایان بازی

من خواستم بعد از برد/باخت یک popup روشن نشان دهد چه کسی برد و در برد انسان تبریک بگوید. این قابلیت در practice و online **وب** با `apps/web/src/ResultDialog.tsx` پیاده و با هر دو نتیجهٔ بازی با ربات تست شده است؛ بازی تازه از popup ممکن است.

**در native هنوز Modal مشابه پیاده نشده است؛ فقط متن برنده وجود دارد.** برای Android/iOS یک popup هم‌سطح وب بساز و یک بازی واقعی تا پایان برای برد و باخت تست کن. از پایان‌یافته بودن state برای جلوگیری از ورودی اضافه استفاده کن و restart تمیز باشد.

### تعداد بازیکنان و چیدمان

من ۳ یا ۴ نفر انتخاب می‌کردم ولی فقط دو رنگ دیده می‌شد. این ایراد در وب و native اصلاح شد: انتخاب تعداد فوراً match تازه با ۸/۱۲/۱۶ مهره می‌سازد و selector از state واقعی مشتق است. رگرسیون ایجاد نکن؛ سه‌نفره و چهارنفره را در RTL و موبایل تست کن.

تیک «تمرین با ربات» و متنش قبلاً در دو خط جدا بود؛ در وب اصلاح شد و هم‌راستا هستند. در نمایشگر کوچک تاس و دکمهٔ ریختن تاس کنار هم‌اند. برد native با ارتفاع صفحه تنظیم می‌شود تا دکمهٔ تاس قابل لمس باشد؛ بقیهٔ تنظیمات با ScrollView قابل دسترسی‌اند.

### ربات و تاس

Easy از حرکت‌های قانونی تصادفی انتخاب می‌کند. Normal به گرفتن مهره، ورود، پیشروی و پایان امتیاز می‌دهد. Hard علاوه بر این خطر و خانه‌های امن را ارزیابی می‌کند. **سطح ربات فقط انتخاب حرکت را عوض می‌کند، نه احتمال تاس.** ربات موتور را دور نمی‌زند.

من چند شش پشت‌سرهم دیدم و خواستم بررسی شود. در تابع واقعی تاس وب ۱۰۰ هزار نمونهٔ واقعی crypto گرفته شد: counts = [16704,16761,16578,16601,16594,16762]، شش ۱۶٫۷۶۲٪ و chi-square = 2.21012. طولانی‌ترین ردیف شش در جریان خام نمونه‌ها ۶ بود. این نمونه تشخیص توزیع است، نه اثبات اتفاق خاص بازی من. احتمال طبیعی هر وجه ۱/۶ است و تکرار شش به‌تنهایی ایراد نیست.

وب `crypto.getRandomValues` و native `expo-crypto.getRandomBytes` دارند، بایت‌های >=252 رد می‌شوند و سپس `%6+1` انجام می‌شود؛ هر وجه ۴۲ مقدار بایت پذیرفته‌شده دارد. بک‌اند commit/client nonce/reveal با HMAC و rejection sampling دارد. تاس آنلاین را سرور تعیین می‌کند؛ نتیجهٔ محلی مدرک رمزنگاری آنلاین ندارد. تست‌های موتور/fair-dice در بررسی آخر ۳۱ مورد پاس شدند. قاعدهٔ پیش‌فرض سومین شش متوالی در یک نوبت، عبور نوبت است. بین «جریان خام نمونه‌ها» و «سه شش در نوبت یک بازیکن» تفاوت هست.

بدون شواهد تاس را دستکاری نکن: ضدتکرار شش، pity، وابستگی به باخت/خرید/سکه/سختی ربات، یا چرخهٔ مصنوعی اعداد ممنوع است. برای بررسی رخداد واقعی سابقهٔ تاس/نوبت قابل مشاهده فراهم کن. history آنلاین وجود دارد؛ history محلی ممکن است نیاز به بهبود داشته باشد. محدودیت تعهد و انتخاب اولیه seed را از FAIR_DICE و SECURITY بخوان؛ ادعای غیرقابل‌تقلب مطلق نکن.

## مهم‌ترین کار بعدی: آنلاین واقعی روی سایت من

**در حال حاضر هیچ سایت یا بک‌اند عمومی از این محیط منتشر نشده است.** فایل دانلودی `mench-classic-colors.html` فقط Practice/ربات را bundle می‌کند و آنلاین ندارد. این فایل جای نسخهٔ کامل وب را نگیرد. کد کامل وب در `apps/web/src/main.tsx` و `Online.tsx` قابلیت آنلاین دارد. دعوت `/join/:code` و ساخت/ورود اتاق/شروع/بررسی تاس/reload با دو مرورگر جدا روی سرور محلی تست شده است.

Android بخش آنلاین دارد ولی آدرس پیش‌فرض `http://127.0.0.1:3001` است؛ روی گوشی این خود گوشی است، نه سرور اینترنتی. قبل از build عمومی `EXPO_PUBLIC_API_URL` را به بک‌اند HTTPS قابل دسترسی تنظیم کن. تنظیم آدرس سرور در UI توسعه موجود است؛ اطلاعات فنی توسعه را بی‌دلیل به جریان محصول نهایی کاربر نیاور.

هدف اول: من و دوستم از دو دستگاه/شبکهٔ واقعی وارد سایت شویم، اتاق بسازیم، لینک بفرستیم، بدون نصب اپ وارد شویم، بازی کامل کنیم، اینترنت را موقتاً قطع/وصل کنیم و هر دو نتیجهٔ یکسان ببینیم. همین تجربه سپس بین Android و مرورگر کار کند.

مسیر کار:

1. سایت و بازی‌های قبلی را بررسی کن. مسیر/زیردامنهٔ مناسب را با قراردادهای همان سایت تعیین کن. به جای بازنویسی سایت، بازی را اضافه کن. امکانات و ظاهر بازی‌های دیگر را خراب نکن.
2. نسخهٔ کامل وب را build/serve کن، PostgreSQL و API واقعی را راه بینداز، TLS/WSS و CORS صحیح تنظیم کن. reverse proxy هم `/api/` و هم `/socket.io/` را به API برساند.
3. `compose.production.yaml`, `infra/Dockerfile.production`, `infra/nginx.conf.template` الگوهای قابل بررسی‌اند، نه الزام جایگزین‌کردن زیرساخت موجود. فایل compose تولیدی سرویس دیتابیس ایجاد نمی‌کند؛ URL دیتابیس موجود از secret file می‌آید. secretها، TLS و دامنه باید واقعاً فراهم شوند؛ example password فقط توسعه است.
4. اگر بازی زیرمسیر سایت می‌آید، مسیرهای root-relative را بازبینی کن: invite در Online از `/join/CODE` روی location.origin ساخته می‌شود؛ تشخیص join در main از pathname شروع‌شونده با `/join/` است. Vite base، assets، PWA manifest/service worker scope/start_url، rewriteهای SPA، API/Socket.IO paths و invite URL باید با محل نصب هماهنگ شوند. service worker بازی نباید routeها و cache سایت/بازی‌های دیگر را کنترل کند. refresh مستقیم لینک دعوت باید کار کند.
5. بک‌اند فعلاً یک مالک برای roomها دارد؛ بدون طراحی ownership مشترک، چند replica یا load-balancer تصادفی راه نینداز. PostgreSQL recovery تک‌instance دارد، صف matchmaking در حافظه است. روی هاست صرفاً static/serverless بدون پشتیبانی WebSocket طولانی‌مدت، همین API را فرضاً قابل اجرا ندان.
6. تجربهٔ سادهٔ دعوت: «بازی آنلاین» → «ساخت اتاق» دو نفره → لینک/کد → دوست از همان backend وارد شود → میزبان با اتصال تعداد انتخاب‌شده شروع کند. برای ۳/۴ نفر همهٔ ظرفیت لازم است. casual guest ممکن است؛ ranked حساب لازم دارد. دعوت لینک وب و کد بین وب/Android را تست کن. برای «بازی سریع» باید حریف واقعاً در صف باشد، نه وانمود کردن به بازیکن واقعی.
7. URL عمومی و دستور اجرا/به‌روزرسانی/rollback/backup مشخص تحویل بده و بعد از انتشار از بیرون محیط سرور تست کن. صرف باز شدن localhost یا پاس شدن تست محلی، تحویل آنلاین نیست.

من در این پیام ادامه و عرضه روی سایت موجودم را می‌خواهم. از مجوزها و اطلاعات موجود در گفت‌وگوی خودت با من استفاده کن. فقط وقتی واقعاً دسترسی/اطلاعات ضروری نداری از من بخواه؛ کارهای مستقل را ادامه بده. برای خرج جدید، انتشار فروشگاهی یا عملیات مخرب روی داده/سایت موجود، مجوز مشخص لازم است. فایل‌های credential، دادهٔ کاربران و config خصوصی را داخل Git یا گزارش نگذار.

## کارهای باقی‌مانده و محدودیت‌هایی که باید صادقانه دنبال شوند

اولویت بالا: آنلاین عمومی روی سایت؛ دعوت دوست؛ هماهنگی طراحی با سایت؛ native winner popup؛ تست کامل native-online و cross-platform روی گوشی واقعی؛ لینک/API production در build؛ مسیرهای PWA و زیرمسیر؛ تجربهٔ اتصال/خطا/reconnect روشن.

برای release موبایل: APK موجود ARM64، development/debug-signed است، نسخهٔ Play/Bazaar production نیست. Identifierهای `com.mench.game` موقت‌اند. production signing/versioning، سیاست حریم خصوصی/شرایط استفاده/حذف حساب و انتشار فروشگاهی باقی‌اند. iOS فقط prebuild پروژه و export JS دارد؛ اجرای native و build Xcode/Pods روی macOS و فرایند فروشگاه انجام نشده است.

برای backend/account: email verification، reset/recovery و Google/Apple/phone login هنوز نداریم. اگر ورود سایت جایگزین می‌شود، migration/linking حساب و sessionها و امکان حذف حساب بررسی شود. بلوک حساب‌ها هویت مهمان را تشخیص نمی‌دهد؛ presence اجتماعی با refresh دستی است. رها کردن بازی، collusion و seasonهای ranked کامل نیستند. تورنمنت پایه abandoned game و زمان‌بندی/forfeit خودکار کامل ندارد. اقتصاد واقعی/پرداخت/store purchases نداریم؛ سکه غیرپولی و cosmetics با ledger فعلی به معنی پرداخت آماده نیست.

برای بخش‌های دیگر master prompt: 2v2، Turbo/Choice Dice، chat کامل، clans، XP/level/profiles گسترده، division/seasonهای پیشرفته و سایر قابلیت‌های آینده را قبل از آنلاین پایدار اولویت نده. موجود بودن primitiveهای پایه را تکمیل تمام محصول معرفی نکن؛ inventory بندهای master را در یک ماتریس «implemented/tested/deployed/pending» بازبینی کن.

برای عملیات/امنیت: گزارش قبلی audit ابزار Expo/native شامل ۲۳ مورد (۱۶ high، ۷ moderate) بود؛ دوباره audit کن، بدون downgrade ناسازگارِ کور. CI محلی آماده است ولی remote workflow اجرا نشده. backup restore محلی و loadهای کوتاه ۱۰۰/۵۰۰/۱۰۰۰ واقعی و یک میلیون نمونه تاس وجود دارند، اما ظرفیت بلندمدت production را ثابت نمی‌کنند. retention/erasure تاریخچه‌ها، backup خارج سرور، alerts، load و security review مستقل و دسترسی‌های staff باقی‌اند.

## شواهد تست و مرز ادعاها

- آخرین تغییر رنگ: `npm run check` پاس؛ ۶۰ تست source پاس، ۲۴ تست وابسته به DB در default صریحاً skip. ۲۴ مورد DB در اجرای جداگانهٔ قبلی با PostgreSQL واقعاً پاس شده بودند؛ برای نسخهٔ محیط جدید دوباره اجرا کن.
- ۱۲ E2E وب بعد از تغییر رنگ پاس؛ پایان بازی انسان/ربات، reset، ۲/۳/۴ نفر، account/social/economy/tournament و online پوشش دارند.
- ۲ platform test پس از typography پاس: Expo browser ↔ desktop و PWA offline. سه خروجی JS Android/iOS/web پاس. بعد از پالت کلاسیک platformها دوباره اجرا نشدند.
- Android 10/API29 x86_64 در شبیه‌ساز نرم‌افزاری بدون KVM واقعاً اجرا شد: فارسی/انگلیسی، ۸/۱۲/۱۶ مهره، تاس واقعی و حرکت قانونی، restart و نوبت ربات. بعد از Samim دوباره smoke پاس شد. یک System UI ANR محیط در گزارش ثبت است؛ benchmark کارایی نیست.
- نسخهٔ ARM64 هم bundle مشابه داشت، امضا/ZIP/ELF با alignment 16KiB بررسی شد. گوشی واقعی تست نشده است. native online و match کامل تا popup تست نشده‌اند.
- آخرین پالت کلاسیک در وب از روی screenshot بررسی شد؛ APK آن build و signature verify شد و pixelهای decodeشدهٔ همهٔ PNGهای آن با سورس تولیدشده دقیقاً تطبیق داده شدند. این نسخهٔ پالت در emulator دوباره اجرا نشده است.
- Gradle هنگام تغییر packages مشترک/PNGهای خارج inputs باندل قبلی را UP-TO-DATE دانست. build helper اکنون bundle تولیدشده را invalid می‌کند. هنگام ساخت با gradlew مستقیم هم مطمئن شو shared source و asset تازه واقعاً وارد APK شده‌اند؛ پاک‌کردن کش خروجیِ تولیدشده یا task inputs درست، لازم است. هش باندل و پیکسل دارایی‌ها را بررسی کن، صرف BUILD SUCCESSFUL کافی نیست.
- نمونهٔ اخیر تاس و ۳۱ تست موتور/RNG و online focused acceptance در `docs/DICE_AND_ONLINE_REVIEW.md` ثبت است.

## اجرای محلی و فایل‌های اصلی

از ریشهٔ سورس با Node مطابق `.nvmrc`:

```sh
npm ci
npm run check
docker compose up -d postgres
# در ترمینال‌های جدا:
npm run dev:api
npm run dev:web
# پس از آماده شدن PostgreSQL و برنامه‌ها:
npm run test:db
npm run test:e2e
CI=1 npm run build:mobile
npm run test:platforms
```

`.env.example` نمونهٔ development است؛ env واقعی را خصوصی تنظیم کن و قرارداد خواندن env را از main/API و Compose بررسی کن. API در توسعه پورت 3001، وب پورت 5173 است و Vite `/api` و `/socket.io` را proxy می‌کند. دو suite E2E/platforms که مالک وب‌سرور هستند را هم‌زمان اجرا نکن. مرورگر Playwright موردنیاز را در محیط جدید نصب/تنظیم کن.

```sh
node scripts/build-game-art.mjs
node scripts/build-offline.mjs /path/to/mench-offline.html
```

دومی فقط practice آفلاین است، نه برنامهٔ وب آنلاین production.

برای native، در `apps/mobile` از `app.json` و dependencies قفل‌شده `expo prebuild` بگیر؛ پوشه‌های generated android/ios در سورس ZIP نیستند و باید ساخته شوند. `.github/workflows/native.yml` فرمان‌های پایه و `infra/scripts/verify-gradle-wrapper.py` checksum رسمی Gradle را دارد. SDK/JDK/NDK باید در ماشین جدید نصب شوند. `infra/scripts/build-android-development.py` helper محیط cloud بوده و مسیر پیش‌فرض toolchain آن `/workspace/mench-toolchains` است؛ portable بودن این مسیر را فرض نکن، آن را به ابزارهای محیط خودت سازگار کن. هیچ node_modules، SDK، signing secret یا دیتابیس production تحویل نیست.

موتور: `packages/game-engine/src/index.ts`
تاس سرور و verifier: `packages/fair-dice/src/`
ربات: `packages/game-bot/src/index.ts`
رنگ/هندسه/هنر: `packages/board-geometry/src/`
رشته‌های فارسی/انگلیسی: `packages/localization/src/index.ts`
وب: `apps/web/src/{main,Practice,Online,ResultDialog,Board,Dice,Avatar}.tsx`, `style.css`
Native: `apps/mobile/{App,Board,Dice,Avatar,Theme}.tsx`, `assets/game`

## معیار تحویل بعدی

کد را inspect کن، نقشهٔ کوتاه و عملی ادامه بده، تغییرات لازم را انجام بده و با tests مرتبط و مرورگر/دستگاه واقعی قابل دسترسی تأیید کن. نتیجهٔ اصلی باید لینک عمومی بازی روی سایت من و دعوت دوستی باشد که واقعاً کار می‌کند، همراه گزارش دقیق اینکه چه چیز تست/منتشر شده و چه چیزی باقی است. popup نتیجه و رنگ‌ها/فونت را حفظ یا تکمیل کن. اسناد وضعیت، مشکلات و دستورات اجرا را به‌روز کن و commitهای روشن بساز. توقف و تأیید پشت‌سرهم برای انتخاب‌های معمول لازم نیست؛ فقط blocker واقعی را توضیح بده.
