# Fair dice v1

Server generates a 256-bit random seed via node:crypto, publishes SHA256(JSON([canonical context, seed])). Context is JSON(["mench-dice-v1", gameId, rollIndex, playerId, stateVersion]). Only after observing this commitment, the honest client generates a fresh 256-bit nonce with WebCrypto. It must not reuse a nonce. Server derives HMAC-SHA256 keyed by decoded seed over JSON([canonical context, nonce, counter]) starting counter 0. Scan output bytes; discard >=252; first accepted byte modulo 6 + 1. Rehash counter+1 only when all bytes rejected. This eliminates modulo bias.
After resolution server reveals seed, nonce, context, published commitment and result. Browser verifier implements SHA256/HMAC independently using WebCrypto. Verification binds to the commitment the client actually observed, not merely a hash supplied after the roll. No economy or engagement data is input.
Threat model: server cannot choose the outcome after commitment against an unpredictable honest client nonce without aborting. Client cannot choose its nonce to select a result while seed is hidden. A server can still withhold/abort games, equivocate across clients or collude with a dishonest client. This is not proof against all operator abuse. Production needs durable public commitment/history and monitoring of selective aborts; do not market unconditional fairness. Local practice is separate and not audited multiplayer.
A fixed simulation fixture tests reproducibility and distribution; secure generation has separate tests. Statistical tests do not prove cryptographic security. TLS, correct commitment timing and audited implementation remain essential.
